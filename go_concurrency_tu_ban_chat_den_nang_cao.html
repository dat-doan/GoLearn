Mở đầu: bản chất trong một đoạn

Concurrency trong Go dựa trên bốn ý. Goroutine là đơn vị công việc rất rẻ. Runtime có một scheduler M:N đưa hàng nghìn goroutine lên vài OS thread. Các goroutine phối hợp bằng hai công cụ: channel (truyền dữ liệu) hoặc lock/atomic (bảo vệ dữ liệu dùng chung). Memory model là bộ luật quy định khi nào giá trị goroutine A ghi chắc chắn được goroutine B nhìn thấy.

Hầu hết lỗi concurrency (race, deadlock, leak) xảy ra khi một trong bốn ý trên bị hiểu sai. Tài liệu đi theo đúng thứ tự đó, từ dưới lên:

  1. Vấn đề gốc: concurrency khác parallelism thế nào, vì sao backend cần nó.

  2. Goroutine: nó là gì về mặt bộ nhớ, tại sao rẻ hơn OS thread.

  3. Scheduler G-M-P: ai quyết định goroutine nào chạy, khi nào, trên thread nào.

  4. Memory model: happens-before và data race, nền móng của mọi công cụ đồng bộ.

  5. Channel: cấu trúc bên trong, hành vi chặn, select.

  6. sync và atomic: Mutex, WaitGroup, Once, Cond, Pool, atomic; khi nào chọn chúng thay vì channel.

  7. context: huỷ và timeout lan truyền qua cây goroutine.

  8. Pattern: worker pool, pipeline, fan-out/fan-in, semaphore, errgroup, graceful shutdown.

  9. Lỗi thường gặp, best practices, công cụ debug và checklist.

Các đoạn code trong tài liệu đã được chạy với Go 1.24, phần lớn kèm -race. Cần Go 1.22+ cho for i := range n và biến vòng lặp riêng mỗi lần lặp. Vài đoạn dùng module ngoài hoặc tính năng Go 1.25 chưa được chạy, và có ghi chú ngay tại chỗ. Kết quả in ra được ghi trong comment; với code có tính không xác định, comment ghi rõ "thứ tự có thể khác".

1. Concurrency vs Parallelism: vấn đề gốc

Concurrency là cách cấu trúc chương trình; parallelism là cách thực thi. Concurrency chia bài toán thành nhiều việc độc lập có thể tiến triển xen kẽ nhau. Parallelism là khi nhiều việc thực sự chạy cùng một thời điểm trên nhiều CPU core. Rob Pike tóm lại: concurrency là dealing with nhiều thứ cùng lúc, parallelism là doing nhiều thứ cùng lúc.

Với việc I/O-bound, ba khoảng chờ chồng lên nhau nên cả ba xong ở t = 180 dù chỉ có 1 core. Với việc CPU-bound, xen kẽ trên 1 core không nhanh hơn tuần tự; phải có core thứ hai mới xong sớm hơn.

Vì sao backend cần concurrency

Một request handler điển hình dành phần lớn thời gian chờ: chờ DB, chờ service khác, chờ client gửi nốt body. Trong lúc chờ, CPU rảnh. Nếu chương trình viết tuần tự, thời gian chờ cộng dồn; nếu viết đồng thời, các khoảng chờ chồng lên nhau. Ví dụ gọi 3 nguồn dữ liệu, mỗi nguồn mất 100 ms:

func fetch(name string) string {
	time.Sleep(100 * time.Millisecond) // giả lập gọi DB/HTTP
	return "data:" + name
}

func main() {
	// Tuần tự
	start := time.Now()
	for _, n := range []string{"user", "order", "stock"} {
		fetch(n)
	}
	fmt.Println("tuần tự:", time.Since(start).Round(10*time.Millisecond))

	// Đồng thời
	start = time.Now()
	var wg sync.WaitGroup
	results := make([]string, 3)
	for i, n := range []string{"user", "order", "stock"} {
		wg.Add(1)
		go func() {
			defer wg.Done()
			results[i] = fetch(n) // mỗi goroutine ghi vào index riêng: không race
		}()
	}
	wg.Wait()
	fmt.Println("đồng thời:", time.Since(start).Round(10*time.Millisecond), results)
}
// Output:
// tuần tự: 300ms
// đồng thời: 100ms [data:user data:order data:stock]

Kết quả này đạt được ngay cả trên 1 core, vì ba goroutine chủ yếu chờ chứ không tính toán. Đó là concurrency mà không cần parallelism.

Concurrency giúp gì, tùy loại công việc

Hệ quả thiết kế: với việc CPU-bound, tạo nhiều goroutine hơn số core không làm nó nhanh hơn. Với việc I/O-bound, giới hạn thật sự nằm ở hệ thống bạn đang gọi tới, nên cần chặn số lượng đồng thời (xem semaphore ở phần 8).

2. Goroutine: một hàm có stack riêng, do runtime quản lý

Goroutine không phải OS thread. Bên trong runtime, nó là một struct g chứa: một stack nhỏ, các thanh ghi đã lưu (PC, SP) để tiếp tục chạy sau này, và trạng thái hiện tại. Lệnh go f(x) chỉ tạo struct đó và đẩy vào hàng đợi; việc chạy nó trên thread nào là chuyện của scheduler (phần 3).

Con số đo thật: giữ 100.000 goroutine cùng sống tốn khoảng 2,6 KB mỗi goroutine.

const n = 100_000
var wg sync.WaitGroup
block := make(chan struct{})
wg.Add(n)
for range n {
	go func() {
		wg.Done()
		<-block // giữ goroutine sống để đo bộ nhớ
	}()
}
wg.Wait()
runtime.ReadMemStats(&after)
fmt.Println("goroutine đang sống:", runtime.NumGoroutine())
fmt.Printf("bộ nhớ thêm: ~%.1f KB/goroutine\n", float64(after.Sys-before.Sys)/n/1024)
close(block)
// Output (Go 1.24, linux/amd64):
// goroutine đang sống: 100001
// bộ nhớ thêm: ~2.6 KB/goroutine

Cùng số lượng đó bằng OS thread sẽ đặt trước hàng trăm GB không gian địa chỉ cho stack. Đây là lý do Go có thể dùng mô hình "mỗi request một goroutine" mà không cần callback hay async/await.

Stack tăng bằng cách sao chép

Đầu mỗi hàm, compiler chèn một phép kiểm tra: stack còn đủ chỗ cho hàm này không? Nếu không, runtime cấp một stack gấp đôi, chép toàn bộ stack cũ sang và sửa các con trỏ trỏ vào stack. Khi GC thấy stack dùng ít, nó thu nhỏ lại. Hệ quả: goroutine bắt đầu rẻ, đệ quy sâu vẫn chạy được (giới hạn mặc định 1 GB trên 64-bit), đổi lại một chi phí sao chép nhỏ khi stack phình ra.

Vòng đời

Chỉ trạng thái Running chiếm một thread. Khi goroutine chờ channel, mutex hay I/O mạng, nó rời khỏi thread và thread đó chạy goroutine khác. Riêng syscall chặn giữ cả thread, nên runtime có cơ chế handoff P ở phần 3.

Bốn quy tắc về vòng đời cần nhớ:

  1. main trả về thì cả chương trình dừng. Mọi goroutine khác bị huỷ ngay, không chạy defer. Muốn đợi thì phải đồng bộ tường minh (WaitGroup, channel).

  2. Không thể "kill" một goroutine từ bên ngoài. Nó chỉ dừng khi hàm của nó return. Muốn dừng sớm, goroutine đó phải tự kiểm tra tín hiệu (ctx.Done(), channel). Đây là gốc của goroutine leak.

  3. Panic không được recover trong bất kỳ goroutine nào sẽ làm sập toàn bộ process. recover ở main không bắt được panic của goroutine khác.

  4. Tham số của go f(x) được tính ngay trong goroutine gọi, còn thân f chạy sau.

func main() {
	go func() {
		time.Sleep(10 * time.Millisecond)
		fmt.Println("không bao giờ in ra")
	}()
	fmt.Println("main kết thúc")
}
// Output:
// main kết thúc

3. Scheduler G-M-P: ai chạy, khi nào, ở đâu

Scheduler của Go là M:N: N goroutine chạy trên M OS thread, với tối đa GOMAXPROCS thread chạy code Go cùng lúc. Nó xoay quanh ba thực thể:

Ký hiệuLà gìVai trò
G (goroutine)Việc cần chạyChứa stack và thanh ghi đã lưu
M (machine)Một OS thread thậtThực thi lệnh máy; kernel xếp lịch M lên CPU core
P (processor)"Giấy phép" được chạy code GoGiữ local run queue (tối đa 256 G) và cache cấp phát bộ nhớ. Số P = GOMAXPROCS

Quy tắc cốt lõi: M phải cầm một P mới được chạy G. Số M có thể nhiều hơn số P (ví dụ khi có thread đang kẹt trong syscall), nhưng số thread đang chạy code Go không bao giờ vượt quá số P.

Với GOMAXPROCS = 2, chỉ G1 và G5 đang thực sự chạy. G4 và các goroutine chờ socket không cầm P nào, nên không làm chậm hai P còn lại.

Vì sao cần P

Trước Go 1.1, scheduler chỉ có G và M với một hàng đợi toàn cục có khoá. Mọi thread tranh nhau một lock, nên càng nhiều core càng chậm. P tách hàng đợi thành từng cái riêng cho mỗi "slot CPU", nên phần lớn thao tác lấy/đẩy G không cần lock toàn cục. Đây là ví dụ điển hình của kỹ thuật giảm tranh chấp: chia nhỏ tài nguyên dùng chung thành phần riêng cho từng worker.

M tìm việc theo thứ tự nào

Khi một G trên M kết thúc hoặc bị chặn, M (đang giữ P) tìm G tiếp theo:

  1. Slot runnext của P (G vừa được tạo/đánh thức, ưu tiên vì cache còn nóng), rồi local run queue.

  2. Cứ 61 lần lên lịch, liếc global run queue một lần để G ở đó không bị bỏ đói.

  3. Global run queue.

  4. Netpoller: G nào có socket đã sẵn sàng đọc/ghi.

  5. Work stealing: chọn ngẫu nhiên một P khác và lấy một nửa local queue của nó.

  6. Không có gì: trả P, M đi ngủ.

Work stealing giúp tải tự cân bằng: một P rảnh sẽ chủ động lấy việc từ P bận, không cần bộ điều phối trung tâm.

Chuyện gì xảy ra khi goroutine bị chặn

Dòng thứ hai là lý do một server Go giữ 10.000 kết nối mà chỉ dùng vài thread. Code trông như I/O chặn, nhưng runtime biến nó thành I/O không chặn bên dưới.

GOMAXPROCS và việc CPU-bound

func work() (s uint64) { // việc CPU-bound thuần
	for i := range uint64(300_000_000) {
		s += i % 7
	}
	return
}

func main() {
	for _, p := range []int{1, 2} {
		runtime.GOMAXPROCS(p)
		start := time.Now()
		var wg sync.WaitGroup
		for range 4 {
			wg.Add(1)
			go func() { defer wg.Done(); work() }()
		}
		wg.Wait()
		fmt.Printf("GOMAXPROCS=%d: %v\n", p, time.Since(start).Round(10*time.Millisecond))
	}
}
// Output trên máy 2 core (số tuyệt đối tuỳ máy, tỉ lệ mới quan trọng):
// GOMAXPROCS=1: 200ms
// GOMAXPROCS=2: 100ms

Bốn goroutine CPU-bound nhưng chỉ nhanh gấp đôi khi có 2 P: số P, không phải số goroutine, quyết định mức song song.

Mặc định GOMAXPROCS bằng số CPU logic. Từ Go 1.25, trên Linux runtime còn tính đến giới hạn CPU của cgroup và tự cập nhật khi giới hạn thay đổi (Go 1.25 release notes, Go blog). Với Go cũ hơn chạy trong container giới hạn 2 CPU trên máy 64 core, GOMAXPROCS sẽ là 64 và process dễ bị throttle, làm tăng tail latency.

Tự quan sát scheduler

$ GODEBUG=schedtrace=50 ./app
SCHED 0ms: gomaxprocs=2 idleprocs=0 threads=4 spinningthreads=1 needspinning=0 idlethreads=1 runqueue=0 [0 0]

gomaxprocs là số P, threads là số M, runqueue là độ dài global queue, [0 0] là độ dài local queue của từng P. Global queue hoặc local queue dài liên tục nghĩa là có nhiều việc sẵn sàng hơn số P xử lý kịp.

4. Memory model: khi nào một lệnh ghi được nhìn thấy

Không có đồng bộ hoá thì không có đảm bảo nào rằng goroutine B thấy giá trị goroutine A đã ghi, hay thấy theo đúng thứ tự A đã ghi. Đây là phần quan trọng nhất của tài liệu: mọi công cụ ở phần 5 và 6 tồn tại để tạo ra các đảm bảo này.

Vì sao thứ tự trong code không phải thứ tự thật

Ba tầng đều được phép sắp xếp lại hoặc trì hoãn lệnh ghi, miễn là một goroutine đơn lẻ không nhận ra:

  • Compiler: đổi thứ tự lệnh, giữ biến trong thanh ghi thay vì đọc lại từ RAM.

  • CPU: thực thi không theo thứ tự, gom lệnh ghi vào store buffer.

  • Cache: mỗi core có cache riêng; giá trị mới đến core khác sau một khoảng trễ.

Một goroutine luôn thấy code của chính nó chạy đúng thứ tự. Goroutine khác thì không, trừ khi hai bên đồng bộ qua một điểm chung.

Data race

Data race xảy ra khi hai goroutine cùng truy cập một vùng nhớ, ít nhất một bên ghi, và không có quan hệ happens-before giữa hai lần truy cập. Ví dụ kinh điển là n++: nó gồm ba bước đọc, cộng, ghi, nên hai goroutine có thể cùng đọc 5 rồi cùng ghi 6.

var wg sync.WaitGroup

// 1. Có data race
n := 0
for range 1000 {
	wg.Add(1)
	go func() { defer wg.Done(); n++ }()
}
wg.Wait()
fmt.Println("race     :", n, "(thường < 1000, mỗi lần chạy một khác)")

// 2. Mutex
var mu sync.Mutex
m := 0
for range 1000 {
	wg.Add(1)
	go func() { defer wg.Done(); mu.Lock(); m++; mu.Unlock() }()
}
wg.Wait()
fmt.Println("mutex    :", m)

// 3. Atomic
var a atomic.Int64
for range 1000 {
	wg.Add(1)
	go func() { defer wg.Done(); a.Add(1) }()
}
wg.Wait()
fmt.Println("atomic   :", a.Load())

// Output (một lần chạy):
// race     : 992 (thường < 1000, mỗi lần chạy một khác)
// mutex    : 1000
// atomic   : 1000

Chạy với go run -race, race detector chỉ ra đúng dòng có lỗi:

  main.main.func1()

Previous write at 0x00c0000121c8 by goroutine 90:

Trong Go không có "race vô hại". Race trên giá trị nhiều word (string, slice, interface, map) có thể đọc ra một giá trị nửa cũ nửa mới, và làm process crash. Ghi map đồng thời thì runtime chủ động dừng chương trình với lỗi fatal error: concurrent map writes.

Happens-before

A happens-before B nghĩa là: mọi lệnh ghi trước A chắc chắn hiển thị với mọi lệnh đọc sau B. Trong cùng một goroutine, thứ tự code là happens-before. Giữa hai goroutine, chỉ các thao tác đồng bộ sau mới tạo ra cạnh happens-before:

Thao tác Ahappens-before B
Lệnh go f()f bắt đầu chạy
Gửi vào channelLần nhận tương ứng hoàn tất
close(ch)Một lần nhận trả về vì channel đã đóng
Nhận từ channel không bufferLần gửi tương ứng hoàn tất
Nhận lần thứ k từ channel buffer CLần gửi thứ k+C hoàn tất (cơ sở của semaphore bằng channel)
mu.Unlock() lần thứ nmu.Lock() lần thứ n+1 trả về
wg.Done()wg.Wait() trả về
Hàm trong once.Do(f) returnMọi once.Do trả về
Một thao tác atomicThao tác atomic quan sát được giá trị của nó (từ Go 1.19, atomic là sequentially consistent)

Sơ đồ này mô tả đúng đoạn code ngay bên dưới.

var msg string

func main() {
	done := make(chan struct{})
	go func() {
		msg = "hello"   // (1) ghi
		close(done)     // (2) close happens-before (3)
	}()
	<-done              // (3) nhận
	fmt.Println(msg)    // (4) chắc chắn thấy "hello"
}

Chuỗi (1) → (2) → (3) → (4) là bắc cầu: (1) trước (2) vì cùng goroutine, (2) trước (3) theo luật channel, (3) trước (4) vì cùng goroutine. Bỏ channel đi thì bắc cầu đứt.

Phản ví dụ: cờ boolean tự chế

var done bool

func main() {
	go func() {
		time.Sleep(10 * time.Millisecond)
		done = true // ghi không đồng bộ
	}()
	for !done { // đọc không đồng bộ
	}
	fmt.Println("thoát vòng lặp")
}

Khi mình chạy thử với Go 1.24 trên amd64, chương trình vẫn thoát được, và đó chính là cái bẫy. Memory model cho phép compiler đọc done một lần rồi lặp mãi, nên đổi phiên bản compiler, kiến trúc CPU hay mức tối ưu là có thể treo. go run -race báo DATA RACE ngay lập tức. Sửa bằng atomic.Bool, hoặc tốt hơn là một channel done để không phải vòng lặp bận.

Quy tắc rút ra: "chạy đúng trên máy tôi" không chứng minh code concurrent đúng. Chỉ có cạnh happens-before mới chứng minh được.

5. Channel: hàng đợi có khoá kèm hàng chờ goroutine

Channel là một hàng đợi FIFO có khoá, kèm hai danh sách goroutine đang chờ gửi và chờ nhận. make(chan T, n) trả về con trỏ tới struct hchan trên heap, nên truyền channel vào hàm là truyền con trỏ; mọi bản sao đều là cùng một channel. Triết lý đi kèm của Go: đừng giao tiếp bằng cách chia sẻ bộ nhớ; hãy chia sẻ bộ nhớ bằng cách giao tiếp. Gửi một giá trị qua channel cũng là chuyển quyền sở hữu giá trị đó.

Trạng thái trong hình: buffer 4 ô đã đầy, hai goroutine G7 và G9 đang xếp hàng chờ gửi. Một goroutine chờ chỉ tốn một sudog nhỏ trong hàng đợi, không tốn thread.

Điều gì xảy ra khi gửi ch <- v

  1. Khoá hchan.lock.

  2. Nếu có goroutine đang chờ trong recvq: chép v thẳng vào stack của goroutine nhận, đánh thức nó (đưa vào run queue). Không đi qua buffer.

  3. Nếu buffer còn chỗ: chép v vào buf[sendx], tăng sendx (vòng tròn).

  4. Nếu không: đóng gói goroutine hiện tại và v thành một sudog, xếp vào sendq, rồi park goroutine. M không bị chặn; nó đi chạy G khác.

Nhận <-ch đối xứng. Trường hợp đặc biệt: khi buffer đầy và có người gửi đang chờ, người nhận lấy phần tử đầu buffer, chuyển giá trị của người gửi vào cuối buffer rồi đánh thức người gửi. Thứ tự FIFO được giữ nguyên.

Hệ quả: channel luôn có một lock và có sao chép dữ liệu. Nó đủ nhanh cho hầu hết việc phối hợp, nhưng chậm hơn mutex hay atomic khi chỉ cần bảo vệ một biến đếm.

  • Chỉ bên gửi (owner) được đóng channel. Bên nhận đóng thì bên gửi sẽ panic khi gửi tiếp. Khi có nhiều bên gửi, một goroutine riêng đợi tất cả gửi xong (WaitGroup) rồi mới đóng.

  • Channel nil chặn mãi, nghe như lỗi nhưng là công cụ: gán ch = nil để tắt một case trong select.

Kiểu có hướng

select

select chờ nhiều thao tác channel cùng lúc và chạy một case đã sẵn sàng. Nếu nhiều case cùng sẵn sàng, nó chọn ngẫu nhiên để không case nào bị bỏ đói, nên đừng dựa vào thứ tự viết case. Có default thì không bao giờ chặn.

result := make(chan string, 1) // buffer 1: goroutine gửi được kể cả khi không ai nhận
go func() {
	time.Sleep(200 * time.Millisecond) // dịch vụ chậm
	result <- "ok"
}()

select {
case r := <-result:
	fmt.Println("kết quả:", r)
case <-time.After(100 * time.Millisecond):
	fmt.Println("timeout")
}

// select với default = thao tác không chặn
q := make(chan int, 1)
q <- 1
select {
case q <- 2:
	fmt.Println("đã gửi")
default:
	fmt.Println("hàng đợi đầy, bỏ qua")
}
// Output:
// timeout
// hàng đợi đầy, bỏ qua

Chú ý result có buffer 1. Nếu không có buffer, sau khi timeout không còn ai nhận, goroutine dịch vụ sẽ chặn mãi ở result <- "ok": một goroutine leak (lỗi #1 ở phần 9).

Mẫu dùng channel nil để tắt case khi gộp hai nguồn:

func merge(a, b <-chan int) []int {
	var out []int
	for a != nil || b != nil {
		select {
		case v, ok := <-a:
			if !ok {
				a = nil // nil channel: case này không bao giờ sẵn sàng nữa
				continue
			}
			out = append(out, v)
		case v, ok := <-b:
			if !ok {
				b = nil
				continue
			}
			out = append(out, v)
		}
	}
	return out
}

Nếu không gán nil, case của channel đã đóng luôn sẵn sàng (trả zero value), và vòng lặp quay bận ăn 100% CPU.

6. Package sync và atomic: bảo vệ trạng thái dùng chung

Channel chuyển quyền sở hữu dữ liệu; sync và atomic bảo vệ dữ liệu nằm yên một chỗ mà nhiều goroutine cùng chạm vào. Hai cách không cạnh tranh nhau; mỗi cách hợp với một dạng bài toán. Chọn sai thì code vẫn chạy, nhưng rối và chậm hơn cần thiết.

Câu hỏi để chọn: dữ liệu này đi từ goroutine này sang goroutine khác, hay ở yên một chỗ cho nhiều goroutine cùng dùng? Bảng dưới đây áp dụng câu hỏi đó cho các tình huống cụ thể.

Mutex

sync.Mutex bảo đảm tại một thời điểm chỉ một goroutine ở trong vùng giữa Lock và Unlock (critical section). Bên trong: đường nhanh là một phép CAS atomic; nếu khoá đang bị giữ, goroutine quay chờ (spin) rất ngắn rồi park. Nếu một goroutine đã chờ quá 1 ms, mutex chuyển sang starvation mode và giao khoá thẳng cho người chờ lâu nhất để không ai bị bỏ đói.

// Cache an toàn cho concurrent: mutex nằm cạnh dữ liệu nó bảo vệ.
type Cache struct {
	mu   sync.RWMutex // bảo vệ data
	data map[string]string
}

func NewCache() *Cache { return &Cache{data: make(map[string]string)} }

func (c *Cache) Get(k string) (string, bool) {
	c.mu.RLock() // nhiều reader cùng lúc
	defer c.mu.RUnlock()
	v, ok := c.data[k]
	return v, ok
}

func (c *Cache) Set(k, v string) {
	c.mu.Lock() // writer độc quyền
	defer c.mu.Unlock()
	c.data[k] = v
}
// 100 goroutine Set + 100 goroutine Get, chạy với -race: không có cảnh báo.

Năm quy tắc với Mutex:

  1. Zero value dùng được ngay, không cần khởi tạo.

  2. Không re-entrant: goroutine đang giữ khoá gọi Lock lần nữa là tự deadlock.

  3. Không được copy sau khi dùng. Struct chứa mutex phải có method receiver là con trỏ; go vet (kiểm tra copylocks) sẽ bắt lỗi này.

  4. Critical section ngắn: không gọi mạng, DB, hay gửi channel khi đang giữ khoá.

  5. Mutex bảo vệ dữ liệu, không bảo vệ code. Đặt nó ngay trên các field nó bảo vệ, kèm comment.

RWMutex chỉ đáng dùng khi đọc chiếm ưu thế lớn và critical section đủ dài; với critical section rất ngắn, chi phí quản lý reader có thể khiến nó chậm hơn Mutex thường. Khi có writer đang chờ, RLock mới sẽ bị chặn để writer không bị bỏ đói, nên gọi RLock lồng nhau trong cùng goroutine có thể deadlock.

WaitGroup

Bộ đếm: Add(n) tăng, Done() giảm, Wait() chặn tới khi về 0. Luôn gọi Add trước lệnh go, không gọi bên trong goroutine; nếu không, Wait có thể thấy bộ đếm bằng 0 và trả về sớm. Từ Go 1.25 có wg.Go(f) gộp Add(1), go và defer Done() làm một, và go vet có bộ kiểm tra waitgroup báo Add đặt sai chỗ (Go 1.25 release notes). Các ví dụ trong tài liệu dùng Add/Done vì được chạy trên Go 1.24.

// Go 1.25+ (chưa chạy kiểm chứng trong tài liệu này)
var wg sync.WaitGroup
for _, url := range urls {
	wg.Go(func() { fetch(url) })
}
wg.Wait()

Once, OnceValue, Pool

var loadConfig = sync.OnceValue(func() map[string]string {
	fmt.Println("đọc config (chỉ 1 lần)")
	return map[string]string{"env": "prod"}
})

var bufPool = sync.Pool{
	New: func() any { return new(bytes.Buffer) },
}

func render(name string) string {
	buf := bufPool.Get().(*bytes.Buffer)
	defer func() {
		buf.Reset() // trả về trạng thái sạch trước khi Put
		bufPool.Put(buf)
	}()
	buf.WriteString("hello, ")
	buf.WriteString(name)
	return buf.String()
}
// 5 goroutine cùng gọi loadConfig(), rồi in:
// đọc config (chỉ 1 lần)
// prod
// hello, Dat

  • sync.Once.Do(f) chạy f đúng một lần; mọi lời gọi khác chờ tới khi f xong. OnceFunc, OnceValue, OnceValues (Go 1.21) gọn hơn và trả được giá trị hoặc lỗi.

  • sync.Pool là kho object tạm có thể bị GC dọn bất cứ lúc nào. Dùng cho buffer, encoder; không dùng làm cache hay connection pool. Luôn Reset trước khi Put.

  • sync.Map chỉ tốt hơn map + Mutex trong hai trường hợp: key ghi một lần rồi đọc rất nhiều, hoặc mỗi goroutine làm việc với tập key riêng. Mặc định hãy dùng map + Mutex vì có kiểu rõ ràng.

  • sync.Cond cho phép goroutine chờ một điều kiện trên dữ liệu do mutex bảo vệ (Wait, Signal, Broadcast). Hiếm khi cần: channel hoặc close thường diễn đạt cùng ý rõ hơn.

atomic

Atomic thao tác trên một giá trị bằng lệnh CPU đặc biệt, không cần park goroutine. Dùng các kiểu có sẵn (Go 1.19+): atomic.Int64, atomic.Bool, atomic.Pointer[T].

type Config struct{ Version int }

func main() {
	// atomic.Pointer: đổi cả object config mà reader không cần lock
	var cfg atomic.Pointer[Config]
	cfg.Store(&Config{Version: 1})

	var reads atomic.Int64
	var wg sync.WaitGroup
	for range 4 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for range 1000 {
				_ = cfg.Load().Version // luôn thấy một Config hoàn chỉnh
				reads.Add(1)
			}
		}()
	}
	cfg.Store(&Config{Version: 2}) // thay thế nguyên khối, không sửa tại chỗ
	wg.Wait()

	// CompareAndSwap: chỉ ghi nếu giá trị vẫn là giá trị mình đã thấy
	var state atomic.Int32
	fmt.Println(state.CompareAndSwap(0, 1)) // true : 0 → 1
	fmt.Println(state.CompareAndSwap(0, 1)) // false: đang là 1
	fmt.Println(reads.Load(), cfg.Load().Version) // 4000 2
}

Giới hạn cần nhớ: hai biến atomic không tạo thành một thao tác atomic. Nếu bất biến liên quan nhiều field (ví dụ balance và history phải khớp nhau), dùng Mutex, hoặc gom chúng vào một struct bất biến rồi thay cả khối bằng atomic.Pointer như ví dụ trên.

7. context: huỷ và timeout lan truyền qua cây goroutine

context.Context giải quyết bài toán "làm sao bảo cả một nhóm goroutine dừng lại", vì goroutine không thể bị kill từ bên ngoài (phần 2). Một request HTTP sinh ra goroutine gọi DB, goroutine đó lại gọi service khác. Khi client ngắt kết nối hoặc hết thời gian, toàn bộ cây công việc đó nên dừng để không tốn tài nguyên vô ích.

Về bản chất, context là một cây. Mỗi nút có một channel Done() sẽ được close khi nút bị huỷ. Huỷ một nút sẽ huỷ mọi nút con của nó, nhưng không ảnh hưởng nút cha. Nó dùng đúng cơ chế phát sóng bằng close ở phần 5.

Khi client ngắt kết nối, query DB và cả hai worker đều nhận tín hiệu dừng cùng lúc. Nhánh WithoutCancel vẫn chạy tiếp để audit log không bị mất.

// queryDB giả lập một truy vấn tôn trọng ctx.
func queryDB(ctx context.Context, d time.Duration) (string, error) {
	select {
	case <-time.After(d):
		return "rows", nil
	case <-ctx.Done():
		return "", ctx.Err() // context.Canceled hoặc context.DeadlineExceeded
	}
}

type reqIDKey struct{} // key riêng kiểu, tránh đụng key của package khác

func worker(ctx context.Context, id int, done chan<- string) {
	for {
		select {
		case <-ctx.Done():
			done <- fmt.Sprintf("worker %d dừng: %v", id, context.Cause(ctx))
			return
		case <-time.After(20 * time.Millisecond):
			// làm một phần việc nhỏ rồi kiểm tra lại ctx
		}
	}
}

func main() {
	// 1. Timeout: request chỉ được phép chạy 50ms
	ctx, cancel := context.WithTimeout(context.Background(), 50*time.Millisecond)
	defer cancel() // luôn gọi để giải phóng timer
	_, err := queryDB(ctx, 200*time.Millisecond)
	fmt.Println("query:", err, errors.Is(err, context.DeadlineExceeded))

	// 2. Huỷ lan truyền: cancel cha → mọi con đều thấy Done
	parent, cancelParent := context.WithCancelCause(context.Background())
	child1, cancel1 := context.WithTimeout(parent, time.Hour)
	defer cancel1()
	child2 := context.WithValue(parent, reqIDKey{}, "abc")
	done := make(chan string, 2)
	go worker(child1, 1, done)
	go worker(child2, 2, done)
	time.Sleep(30 * time.Millisecond)
	cancelParent(errors.New("client ngắt kết nối"))
	fmt.Println(<-done)
	fmt.Println(<-done)
}
// Output (hai dòng worker có thể đổi thứ tự):
// query: context deadline exceeded true
// worker 1 dừng: client ngắt kết nối
// worker 2 dừng: client ngắt kết nối

Context chỉ là tín hiệu, không phải lệnh cưỡng chế. Code nhận ctx phải tự kiểm tra ctx.Done() ở các điểm chờ, hoặc truyền ctx xuống thư viện có hỗ trợ (http.NewRequestWithContext, db.QueryContext). Một vòng lặp CPU-bound không kiểm tra ctx sẽ chạy tới hết bất kể đã bị huỷ.

Quy ước khi dùng context:

  • Context là tham số đầu tiên, tên ctx; không lưu trong struct (trừ khi struct đó chính là một request).

  • Có With... trả về cancel thì luôn defer cancel(), kể cả với timeout; không thì tài nguyên của nút con chỉ được giải phóng khi cha bị huỷ. go vet (kiểm tra lostcancel) báo lỗi này.

  • WithValue chỉ cho dữ liệu phạm vi request đi xuyên API (request ID, thông tin xác thực), không dùng để truyền tham số tuỳ chọn. Key là kiểu riêng không export.

  • Không truyền nil context; chưa biết dùng gì thì dùng context.TODO().

  • Trong HTTP server, lấy ctx từ r.Context(): nó bị huỷ khi client ngắt kết nối hoặc handler trả về.

8. Pattern nâng cao: ghép các khối cơ bản

Mọi pattern dưới đây chỉ là cách ghép goroutine, channel, WaitGroup và context theo hai luật: (1) mỗi channel có đúng một bên sở hữu, bên đó gửi và đóng; (2) mọi goroutine đều có đường thoát rõ ràng, thường là channel đầu vào bị đóng hoặc ctx.Done(). Tất cả ví dụ trong phần này đã chạy với -race và không có cảnh báo.

8.1 Worker pool: giới hạn số goroutine xử lý

Dùng khi có nhiều việc và muốn chặn số việc chạy cùng lúc (số kết nối DB, CPU). N goroutine cố định cùng đọc một channel jobs; channel tự chia việc cho ai đang rảnh.

type Job struct{ ID int }
type Result struct {
	JobID  int
	Output string
}

func process(ctx context.Context, j Job) Result {
	time.Sleep(10 * time.Millisecond) // giả lập I/O
	return Result{j.ID, fmt.Sprintf("job-%d xong", j.ID)}
}

// workerPool: số goroutine cố định đọc từ một channel jobs chung.
func workerPool(ctx context.Context, jobs <-chan Job, workers int) <-chan Result {
	results := make(chan Result)
	var wg sync.WaitGroup
	for range workers {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for j := range jobs { // dừng khi jobs bị đóng
				select {
				case results <- process(ctx, j):
				case <-ctx.Done():
					return
				}
			}
		}()
	}
	go func() {
		wg.Wait()      // mọi worker đã thoát
		close(results) // chỉ đóng khi không còn ai gửi
	}()
	return results
}

func main() {
	ctx := context.Background()
	jobs := make(chan Job)
	go func() {
		defer close(jobs) // producer sở hữu jobs nên producer đóng
		for i := range 20 {
			jobs <- Job{ID: i}
		}
	}()

	start := time.Now()
	n := 0
	for range workerPool(ctx, jobs, 5) {
		n++
	}
	fmt.Printf("%d kết quả trong %v (20 job × 10ms / 5 worker)\n", n, time.Since(start).Round(10*time.Millisecond))
}
// Output:
// 20 kết quả trong 40ms (20 job × 10ms / 5 worker)

Chỗ hay sai nhất là ai đóng results. Năm worker cùng gửi vào results, nên không worker nào được đóng nó. Một goroutine riêng đợi cả năm thoát (wg.Wait) rồi mới đóng.

8.2 Pipeline, fan-out, fan-in

Pipeline nối các stage bằng channel: mỗi stage nhận <-chan in, trả <-chan out, và tự đóng out khi xong. Fan-out: nhiều goroutine cùng đọc một channel để chia tải stage chậm. Fan-in: gộp nhiều channel về một.

// Mỗi stage: nhận <-chan in, trả <-chan out, tự đóng out khi xong.
func generate(ctx context.Context, nums ...int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for _, n := range nums {
			select {
			case out <- n:
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}

func square(ctx context.Context, in <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for n := range in {
			select {
			case out <- n * n:
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}

// fanIn gộp nhiều channel thành một.
func fanIn(ctx context.Context, cs ...<-chan int) <-chan int {
	out := make(chan int)
	var wg sync.WaitGroup
	for _, c := range cs {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for v := range c {
				select {
				case out <- v:
				case <-ctx.Done():
					return
				}
			}
		}()
	}
	go func() { wg.Wait(); close(out) }()
	return out
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel() // dừng mọi stage nếu main thoát sớm

	src := generate(ctx, 1, 2, 3, 4, 5, 6)
	// fan-out: 3 goroutine square cùng đọc từ src
	merged := fanIn(ctx, square(ctx, src), square(ctx, src), square(ctx, src))

	sum := 0
	for v := range merged {
		sum += v
	}
	fmt.Println("tổng bình phương:", sum)
}
// Output:
// tổng bình phương: 91

Mọi lệnh gửi đều nằm trong select với ctx.Done(). Nếu consumer dừng đọc giữa chừng (ví dụ gặp lỗi rồi return), defer cancel() giải phóng mọi stage đang chặn ở lệnh gửi. Thiếu điều đó, mỗi stage là một goroutine leak. Fan-out làm mất thứ tự; cần thứ tự thì gắn index vào mỗi phần tử và sắp lại ở cuối.

8.3 Semaphore: giới hạn đồng thời mà không cần pool

Khi mỗi việc vẫn có goroutine riêng nhưng chỉ cho phép K việc chạy cùng lúc, dùng channel buffer K làm semaphore. Nó dựa vào luật happens-before của channel có buffer ở phần 4.

sem := make(chan struct{}, 3) // tối đa 3 việc cùng lúc
var running, peak atomic.Int32
var wg sync.WaitGroup

for range 10 {
	wg.Add(1)
	go func() {
		defer wg.Done()
		sem <- struct{}{}        // lấy 1 slot (chặn nếu đã đủ 3)
		defer func() { <-sem }() // trả slot

		cur := running.Add(1)
		for {
			p := peak.Load()
			if cur <= p || peak.CompareAndSwap(p, cur) {
				break
			}
		}
		time.Sleep(20 * time.Millisecond)
		running.Add(-1)
	}()
}
wg.Wait()
fmt.Println("số việc chạy đồng thời cao nhất:", peak.Load())
// Output:
// số việc chạy đồng thời cao nhất: 3

So với worker pool: semaphore đơn giản hơn khi số việc vừa phải và đã biết trước; worker pool hợp hơn khi việc đến liên tục từ một nguồn, vì nó không tạo thêm goroutine cho mỗi việc.

8.4 Chạy song song, lỗi đầu tiên huỷ phần còn lại (errgroup)

Bài toán hay gặp nhất ở backend: gọi N dịch vụ song song, một cái lỗi thì bỏ cả và trả lỗi. Dưới đây là phần lõi của errgroup viết tay để thấy cơ chế: WaitGroup + Once + context.

func runAll(ctx context.Context, tasks []func(context.Context) error) error {
	ctx, cancel := context.WithCancelCause(ctx)
	defer cancel(nil)
	var wg sync.WaitGroup
	var once sync.Once
	var firstErr error
	for _, t := range tasks {
		wg.Add(1)
		go func() {
			defer wg.Done()
			if err := t(ctx); err != nil {
				once.Do(func() { firstErr = err; cancel(err) })
			}
		}()
	}
	wg.Wait()
	return firstErr
}
// Với A (10ms, ok), B (30ms, lỗi), C (500ms, ok):
// A xong
// C bị huỷ
// err: B lỗi | sau 30ms

Trong code thật, dùng thư viện golang.org/x/sync/errgroup. SetLimit giúp nó kiêm luôn vai trò semaphore. Đoạn dưới chưa được chạy trong tài liệu này vì môi trường kiểm chứng không tải được module ngoài:

g, ctx := errgroup.WithContext(ctx)
g.SetLimit(10) // tối đa 10 goroutine cùng lúc
for _, url := range urls {
	g.Go(func() error { return fetch(ctx, url) })
}
if err := g.Wait(); err != nil { // lỗi đầu tiên; ctx đã bị huỷ
	return err
}

8.5 Graceful shutdown

Khi Kubernetes dừng pod, process nhận SIGTERM. Server cần ngừng nhận request mới, cho request đang chạy hoàn tất trong một thời hạn, rồi mới thoát.

func main() {
	// ctx bị huỷ khi nhận SIGINT (Ctrl+C) hoặc SIGTERM (Kubernetes dừng pod)
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	mux := http.NewServeMux()
	mux.HandleFunc("/slow", func(w http.ResponseWriter, r *http.Request) {
		time.Sleep(300 * time.Millisecond) // request đang dở khi có tín hiệu dừng
		fmt.Fprintln(w, "ok")
	})
	srv := &http.Server{Addr: "127.0.0.1:8089", Handler: mux}

	go func() {
		if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
			fmt.Println("listen:", err)
		}
	}()

	<-ctx.Done()
	fmt.Println("nhận tín hiệu dừng, ngừng nhận request mới")

	// Cho request đang chạy tối đa 5s để hoàn tất
	shutdownCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()
	if err := srv.Shutdown(shutdownCtx); err != nil {
		fmt.Println("shutdown:", err)
	}
	fmt.Println("đã tắt sạch")
}
// Khi thử: gửi 1 request /slow rồi gửi SIGTERM sau 50ms
// nhận tín hiệu dừng, ngừng nhận request mới
// client nhận: 200 OK      ← request đang dở vẫn hoàn tất
// đã tắt sạch

shutdownCtx được tạo từ context.Background(), không phải từ ctx: ctx đã bị huỷ rồi, dùng nó thì Shutdown sẽ bỏ ngang ngay lập tức.

8.6 Giới hạn tốc độ (rate limiting)

Semaphore giới hạn số việc đang chạy; rate limiter giới hạn số việc bắt đầu mỗi giây. Hai thứ này khác nhau: gọi một API cho phép 100 request/giây thì cần rate limiter, còn bảo vệ connection pool 20 kết nối thì cần semaphore. Trong code thật, dùng golang.org/x/time/rate (token bucket, có limiter.Wait(ctx) tôn trọng huỷ). Với nhu cầu rất đơn giản, đọc từ một time.Ticker trước mỗi việc cũng đủ, nhớ defer ticker.Stop().

9.1 Goroutine leak: lỗi phổ biến và khó thấy nhất

Goroutine bị chặn vĩnh viễn không bao giờ được GC thu hồi, vì runtime không biết nó sẽ không bao giờ chạy tiếp. Stack của nó và mọi thứ nó tham chiếu đều nằm lại trong RAM.

// leak: nếu caller bỏ đi sau timeout, goroutine bên trong chặn mãi ở ch <- ...
func searchLeak(timeout time.Duration) string {
	ch := make(chan string) // không buffer
	go func() {
		time.Sleep(50 * time.Millisecond)
		ch <- "kết quả" // không ai nhận nữa → chặn vĩnh viễn
	}()
	select {
	case r := <-ch:
		return r
	case <-time.After(timeout):
		return "timeout"
	}
}

func searchFixed(timeout time.Duration) string {
	ch := make(chan string, 1) // buffer 1: lệnh gửi luôn hoàn tất
	// ... phần còn lại giống hệt searchLeak
}

func main() {
	for range 100 {
		searchLeak(10 * time.Millisecond)
	}
	time.Sleep(100 * time.Millisecond)
	fmt.Println("sau searchLeak :", runtime.NumGoroutine(), "goroutine")

	for range 100 {
		searchFixed(10 * time.Millisecond)
	}
	time.Sleep(100 * time.Millisecond)
	fmt.Println("sau searchFixed:", runtime.NumGoroutine(), "goroutine (100 cái cũ vẫn kẹt)")
}
// Output:
// sau searchLeak : 101 goroutine
// sau searchFixed: 101 goroutine (100 cái cũ vẫn kẹt)

searchFixed không tạo thêm goroutine kẹt nào; 100 goroutine còn lại là từ searchLeak. Trong server chạy nhiều ngày, mỗi request timeout để lại một goroutine kẹt, và số đó tăng mãi. Câu hỏi phải tự trả lời trước mỗi lệnh go: goroutine này kết thúc khi nào, và điều gì bảo đảm nó kết thúc?

Các nguồn leak khác hay gặp: for v := range ch với channel không bao giờ bị đóng; stage pipeline gửi không kèm ctx.Done(); time.Ticker không Stop; HTTP response body không Close.

9.2 Deadlock

Runtime chỉ phát hiện deadlock khi tất cả goroutine đều bị chặn. Trong server thật luôn có goroutine khác đang sống (listener, timer), nên deadlock một phần thường chỉ hiện ra là request treo, không có thông báo gì.

Ca 1, gửi mà không ai nhận:

func main() {
	ch := make(chan int)
	ch <- 1 // không có goroutine nào nhận
}
// fatal error: all goroutines are asleep - deadlock!
// goroutine 1 [chan send]:

Ca 2, chờ xong rồi mới đọc. Đây là lỗi rất hay gặp khi mới học:

var wg sync.WaitGroup
results := make(chan int)
for i := range 3 {
	wg.Add(1)
	go func() { defer wg.Done(); results <- i }()
}
wg.Wait()           // chờ 3 goroutine gửi xong...
close(results)      // ...nhưng chúng chỉ gửi xong khi có người nhận
for r := range results {
	fmt.Println(r)
}
// fatal error: all goroutines are asleep - deadlock!
// goroutine 1 [sync.WaitGroup.Wait]:

Sửa: chuyển wg.Wait(); close(results) vào một goroutine riêng (như worker pool ở 8.1) để main đọc song song với việc chờ.

Ca 3, hai lock khoá ngược thứ tự:

go func() { // khoá A rồi B
	muA.Lock(); defer muA.Unlock()
	time.Sleep(10 * time.Millisecond)
	muB.Lock(); defer muB.Unlock()
}()
go func() { // khoá B rồi A: thứ tự ngược
	muB.Lock(); defer muB.Unlock()
	time.Sleep(10 * time.Millisecond)
	muA.Lock(); defer muA.Unlock()
}()
// fatal error: all goroutines are asleep - deadlock!

Sửa: quy ước một thứ tự khoá toàn cục (luôn A trước B), hoặc thiết kế lại để không cần giữ hai lock cùng lúc. Không có sleep thì lỗi này chỉ xảy ra thỉnh thoảng dưới tải, nên rất khó tái hiện.

9.3 Race trên map, channel đã đóng, mutex bị copy

// Ghi map từ 100 goroutine
m := map[int]int{}
for i := range 100 {
	wg.Add(1)
	go func() { defer wg.Done(); m[i] = i }()
}
// fatal error: concurrent map writes

fatal error khác panic: không thể recover. Sửa bằng map + Mutex (xem Cache ở phần 6).

ch := make(chan int, 1)
close(ch)
ch <- 1
// panic: send on closed channel

Xảy ra khi bên nhận hoặc một trong nhiều bên gửi tự đóng channel. Sửa bằng luật owner ở phần 5. Muốn phía nhận báo "dừng lại" cho phía gửi thì dùng context hoặc một channel done riêng, không đóng channel dữ liệu.

type Counter struct {
	mu sync.Mutex
	n  int
}

func (c Counter) Inc() { // receiver giá trị: copy cả mutex
	c.mu.Lock()
	c.n++
	c.mu.Unlock()
}
// c.Inc() xong, c.n vẫn là 0.
// go vet: Inc passes lock by value: Counter contains sync.Mutex

9.4 Panic trong goroutine làm sập cả server

recover chỉ bắt được panic trong cùng goroutine. net/http tự recover panic trong handler, nhưng goroutine bạn tự tạo trong handler thì không được bảo vệ. Với goroutine sống lâu (worker, consumer), bọc thân hàm:

func safeGo(log func(any), f func()) {
	go func() {
		defer func() {
			if r := recover(); r != nil {
				log(r) // ghi log kèm stack, đếm metric
			}
		}()
		f()
	}()
}

Chỉ recover ở ranh giới goroutine để biến panic thành lỗi có kiểm soát; không dùng nó thay cho xử lý lỗi bình thường.

9.5 time.After trong vòng lặp nóng

Mỗi lần gọi time.After tạo một timer mới. Trước Go 1.23, timer chưa kích hoạt không được GC thu hồi, nên select với time.After(time.Minute) trong vòng lặp nhận hàng nghìn message mỗi giây gây tăng bộ nhớ. Từ Go 1.23, timer không còn tham chiếu được thu hồi, nhưng vẫn tốn một lần cấp phát mỗi vòng. Với vòng lặp nóng, tạo một time.NewTimer bên ngoài và Reset mỗi vòng.

10. Best practices

Nguyên tắc chung: concurrency là chi phí, không phải tính năng. Mỗi goroutine thêm vào là thêm một thứ tự thực thi có thể xảy ra. Chỉ thêm khi đã biết nó mang lại gì (giảm latency, tăng throughput), và giữ phần concurrent càng nhỏ, càng tập trung một chỗ càng tốt.

Thiết kế

  1. Bắt đầu tuần tự, đo, rồi mới thêm concurrency ở đúng chỗ nghẽn. Code tuần tự đúng dễ biến thành code concurrent đúng hơn là ngược lại.

  2. API đồng bộ, người gọi quyết định concurrency. Viết func Fetch(ctx, id) (Data, error) thay vì hàm tự bật goroutine rồi trả channel. Người gọi luôn có thể tự bọc go; ngược lại thì không.

  3. Mỗi goroutine có chủ và có đường thoát. Ai tạo goroutine thì chịu trách nhiệm đợi nó kết thúc. Tránh "bắn rồi quên" (go f() không ai đợi).

  4. Ưu tiên không chia sẻ. Dữ liệu bất biến, mỗi goroutine ghi vào vùng riêng (results[i]), hoặc chuyển quyền sở hữu qua channel. Chỉ dùng lock khi thật sự phải chia sẻ trạng thái thay đổi.

  5. Luôn có giới hạn. Mọi nơi tạo goroutine theo dữ liệu đầu vào đều cần trần: worker pool, semaphore, SetLimit. Mọi hàng đợi cần kích thước cố định và cách xử lý khi đầy (chờ, từ chối, hay bỏ).

Channel

  1. Mỗi channel có đúng một owner: owner tạo, gửi, đóng, và trả ra <-chan T cho bên ngoài.

  2. Buffer 0 hoặc 1 là mặc định. Con số khác cần lý do cụ thể, ví dụ đúng bằng số việc đã biết trước. Buffer lớn thường chỉ che giấu vấn đề tốc độ không khớp.

  3. Mọi lệnh gửi/nhận có thể chặn lâu thì đặt trong select với ctx.Done().

  4. Dùng chan struct{} cho tín hiệu và close để phát sóng tới nhiều bên nhận.

Lock và atomic

  1. Mutex đặt cạnh dữ liệu nó bảo vệ, không export, kèm comment ghi rõ bảo vệ field nào.

  2. Lock rồi defer Unlock ngay dòng sau, trừ khi cần mở khoá sớm vì lý do hiệu năng đã đo.

  3. Không gọi I/O, callback của người khác, hay gửi channel khi đang giữ lock.

  4. Dùng kiểu atomic có sẵn (atomic.Int64, atomic.Pointer[T]) thay cho hàm atomic.AddInt64(&x, 1) trên biến thường; kiểu có sẵn không thể vô tình bị đọc không atomic.

Context và lỗi

  1. ctx là tham số đầu tiên của mọi hàm có I/O hoặc có thể chạy lâu, và được truyền xuống tới tận lời gọi DB/HTTP.

  2. defer cancel() ngay sau mọi With....

  3. Gọi song song có thể lỗi thì dùng errgroup thay vì tự ghép WaitGroup + channel lỗi.

  4. Goroutine sống lâu có recover ở ranh giới và ghi log kèm stack.

Kiểm chứng và vận hành

  1. CI chạy go test -race ./... và go vet ./.... Race detector chỉ bắt được race trên đường code thực sự chạy, nên test cần chạy các đường concurrent.

  2. Test kiểm tra không leak goroutine (goleak) cho package có tạo goroutine.

  3. Xuất metric số goroutine (runtime.NumGoroutine, hoặc có sẵn trong client Prometheus) và cảnh báo khi nó tăng liên tục. Đường số goroutine đi lên mãi là dấu hiệu leak rõ nhất.

  4. Graceful shutdown cho mọi service: bắt SIGTERM, ngừng nhận việc mới, chờ việc đang chạy có giới hạn thời gian.

  5. Dùng Go ≥ 1.25 khi chạy trong container để GOMAXPROCS tự khớp giới hạn CPU; với Go cũ hơn, đặt GOMAXPROCS thủ công hoặc dùng thư viện automaxprocs.

11. Công cụ phát hiện và gỡ lỗi

Lỗi concurrency hiếm khi lộ ra khi đọc code hay chạy thử vài lần, nên cần công cụ nhìn vào runtime. Mỗi công cụ dưới đây trả lời một câu hỏi khác nhau.

Race detector

Race detector gắn thêm code theo dõi vào mọi truy cập bộ nhớ và ghi lại quan hệ happens-before giữa các goroutine. Nó không báo nhầm: đã báo là có race thật. Nhưng nó chỉ thấy race trên đường code đã thực sự chạy, nên test không chạy đoạn concurrent thì nó không thấy. Chi phí lớn (theo tài liệu Go, bộ nhớ tăng khoảng 5–10 lần, thời gian chạy khoảng 2–20 lần), nên thường bật trong CI và môi trường staging, không bật trên production.

Xem goroutine đang kẹt ở đâu

import _ "net/http/pprof" // đăng ký /debug/pprof/* vào DefaultServeMux

func main() {
	go http.ListenAndServe("localhost:6060", nil) // chỉ mở cho localhost/nội bộ
	// ... ứng dụng chính
}
$ curl -s 'localhost:6060/debug/pprof/goroutine?debug=1' | head
$ go tool pprof http://localhost:6060/debug/pprof/goroutine

Với debug=1, các goroutine có cùng stack được gộp và đếm. Khi có leak, bạn sẽ thấy một dòng kiểu "10342 @ ... chan send" chỉ thẳng vào hàm đang kẹt. Không mở endpoint pprof ra internet: nó lộ thông tin nội bộ và có thể bị dùng để làm quá tải process.

Test không leak

func TestMain(m *testing.M) {
	goleak.VerifyTestMain(m) // test fail nếu còn goroutine lạ khi kết thúc
}

Hai đoạn goleak và synctest trong phần này chưa được chạy kiểm chứng trong tài liệu (cần module ngoài hoặc Go 1.25).

12. Tổng kết: mental model, checklist, lộ trình luyện tập

Nếu chỉ nhớ một điều: goroutine thì rẻ, còn việc phối hợp chúng mới là phần khó. Runtime lo việc chạy goroutine. Phần của bạn là bảo đảm ba điều: mọi dữ liệu dùng chung đều có cạnh happens-before; mọi goroutine đều có đường thoát; và mọi nguồn tạo việc đều có giới hạn.

Checklist trước khi merge code concurrent

  • Mỗi lệnh go có câu trả lời cho "khi nào goroutine này kết thúc, ai đợi nó?"

  • Mỗi dữ liệu dùng chung có đúng một cơ chế bảo vệ (lock, atomic, hoặc chỉ một goroutine chạm vào)

  • Mỗi channel có một owner, đóng đúng một lần, bên nhận không đóng

  • Lệnh gửi/nhận có thể chặn lâu nằm trong select với ctx.Done()

  • ctx được truyền xuống mọi lời gọi I/O; mọi With... có defer cancel()

  • Số goroutine tạo theo dữ liệu đầu vào có trần

  • wg.Add nằm trước go; struct chứa mutex dùng receiver con trỏ

  • Không giữ lock khi gọi I/O hoặc gửi channel; nhiều lock thì khoá theo thứ tự cố định

  • Goroutine sống lâu có recover ở ranh giới

  • go vet ./... và go test -race ./... sạch

Lộ trình luyện tập

Mỗi bài xây trên bài trước. Làm xong bài nào thì chạy lại với -race và in runtime.NumGoroutine() ở cuối để chắc chắn không leak.

  1. Gọi 3 API song song với WaitGroup, rồi đổi sang errgroup có timeout chung 200 ms. Quan sát điều gì xảy ra khi một API lỗi.

  2. Tái hiện từng lỗi ở phần 9, đọc thông báo lỗi, rồi sửa. Mục tiêu là nhận ra lỗi qua triệu chứng.

  3. Viết các kiểu counter: Mutex, atomic, và một goroutine duy nhất sở hữu biến đếm, nhận lệnh qua channel. Viết benchmark (go test -bench . -cpu 1,2,4,8) để thấy chi phí thật của từng cách.

  4. Crawler có giới hạn: tối đa 5 request cùng lúc, không crawl trùng URL (map + Mutex), dừng khi ctx bị huỷ.

  5. Pipeline xử lý file log: đọc dòng, parse (fan-out 4 worker), đếm theo status code, in kết quả. Thêm tuỳ chọn dừng sớm sau N dòng mà không leak stage nào.

  6. HTTP service hoàn chỉnh: handler gọi 2 service phụ song song, có timeout theo request, graceful shutdown, endpoint pprof nội bộ, metric số goroutine. Dùng hey hoặc wrk bắn tải, rồi xem goroutine profile.

  7. Đọc mã nguồn runtime: src/runtime/chan.go (hàm chansend, chanrecv) và src/runtime/proc.go (hàm schedule, findRunnable). Sau phần 3 và 5, phần lớn code ở đó sẽ đọc được.
